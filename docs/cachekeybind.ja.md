# cachekeybind 利用ガイド

`cachekeybind` は Go の構造体からキャッシュキーのメソッドを生成するパッケージです。
キャッシュした結果が何に依存しているかをフィールドに印を付けて generator を実行すれ
ば、呼び出し側で文字列を連結することはなくなります。

手書きのキーは静かに壊れます。型の identity を書き忘れると、同じフィールド値を持つ
別のキー型が同じエントリに届く。最初の呼び出し元の結果が、次の呼び出し元への答えに
なります。古い答えが返るのではなく、間違った答えが返る。フレーミングなしに連結すれ
ば `"ab"+"c"` と `"a"+"bc"` が同じエントリになります。どちらもエラーとしては現れま
せん。現れるのは、ある利用者に別の利用者のデータが見えている、という形です。この
静けさが、このパッケージが相手にしているものです。

一方で、依存関係の集合を推測することはしません。印は opt-in で、印を付けなかった依
存はキーに入りません。その線がなぜそこにあるのかは
[生成が保証すること](#生成が保証すること)を参照してください。

## 書くものと、得られるもの

書くのは tag を付けた構造体と `go:generate` 行です。

```go
package app

//go:generate go run github.com/shibukawa/tinybind-go/cmd/tinybind-gen -dir .

type UserSummary struct {
	UserID string `cache:"key"`
	Page   int    `cache:"key"`
	Name   string
	Total  int
}
```

得られるのはメソッド 1 つと assertion 1 つです。

```go
// Code generated by tinybind; DO NOT EDIT.

var _ cachekeybind.CacheKey = UserSummary{}

func (v UserSummary) CacheKey() string {
	return cachekeybind.KeyString("example.com/app.UserSummary") +
		cachekeybind.KeyString(v.UserID) +
		cachekeybind.KeyInt(v.Page)
}
```

`Name` と `Total` は問い合わせではなく結果なので、キーに入りません。印を付けるとい
う仕組みは、そのためにあります。

ランタイムの interface はメソッド 1 つです。

```go
type CacheKey interface {
	CacheKey() string
}
```

返る文字列はフィールドの値を平文で持ちます。スコープの prefix と連結するのは安全で
すが、ブラウザに届けてはいけません。

## `cache` tag

綴りは 1 つだけです。

| 綴り | 書く場所 | 意味 |
|---|---|---|
| `cache:"key"` | exported なフィールド | そのフィールドがキーの一部になる |

印のないフィールドはキーに入りません。除外の綴りはありません。除外すべきものが最初
から入っていないからです。他のオプションもありません。identity が完全に導出される
からです。

## なぜ opt-in なのか

キャッシュに渡す構造体が、キー専用ではなくストレージのエンティティであることが多い
からです。

```go
type Reading struct {
	Sensor  string  `dynamo:"sensor,partitionkey" cache:"key"`
	At      int64   `dynamo:"at,sortkey"          cache:"key"`
	Celsius float64 `dynamo:"celsius"`
}
```

エンティティのフィールドは、その大半が fetch の返してきたものです。既定で全部入りに
すると `Celsius` がキーに入ります。すると、そのキーを組み立てるために、lookup が取り
に行かずに済ませようとしている値そのものが必要になる。エンティティに対しては、既定
で全部入りは「遅い」のではなく成立しません。

`cache` の印と `dynamo` や `firestore` の tag との整合は検査しません。2 つは別の問い
に答えているからです。ストレージのキーは「その行はどこにあるか」を、キャッシュキー
は「その結果は何に依存したか」を表します。両方向に正当にズレます。パーティションキー
だけでリストをキャッシュすれば狭くなり、保存されないページ番号を含めれば広くなる。
検査を入れると、正しいコードで発火します。

## 1 構造体につき 1 キー

1 つの構造体が持つキーは 1 つです。複数のフィールドに印を付ければ、キーは複合になり
ます。

同じエンティティを 2 種類のクエリでキャッシュしたい場合は、構造体を 2 つ定義してく
ださい。後述の identity はパッケージパスと型名から導出されますが、それが無償で一意な
のは 1 対 1 の関係が保たれている間だけです。1 つの型が 2 つのキーを持てば、その名前を
書く必要が出てきます。それは、このパッケージが取り除こうとしている「書き直し」その
ものです。

## identity

identity は `<パッケージパス>.<型名>` です。どちらも導出されます。宣言されるものが
何もないので、忘れられるものも何もありません。

**キーのバージョンはありません。** 検討したうえで落としました。バージョンとは、フィー
ルドは変わらないまま結果の*意味*が変わったときに、上げるのを覚えておかなければなら
ない数字です。そして上げ忘れは静かに起きます。つまり失敗を閉じるのではなく、移動さ
せるだけです。それはこのパッケージが減らそうとしている失敗の種類であって、増やすも
のではありません。

意味の変化に対する無効化はデプロイの仕事であり、このモジュールは既にそう言っていま
す。`CacheStore` はエントリを列挙も無効化もせず、ランタイムが頼る除去経路は期限切れ
だけです。フィールドが変わらないまま意味が変わったときは、デプロイ側に既にある手段
を使ってください。

- **ストアをビルドまたはリリース単位で名前空間に分ける。** ビルド識別子をキーに含め
  るフレームワークは、デプロイのたびに既に無効化しています。コードを変えた、という
  最も多いケースはこれで尽きます。
- **該当する prefix を flush する。** scope の prefix があるので範囲削除になります。
- **TTL を待つ。** それが答えになる程度に短ければ。

Go の型名を変えても全キーが変わり、コンパイラが呼び出し箇所を全部見つけてくれます。
キー専用の構造体なら現実的な選択肢です。ただしストレージのエンティティでは避けてくだ
さい。型名は Datastore の kind やテーブルのマッピングに供給されるので、リネームは
副作用としてストレージの参照先を変えてしまいます。

## フィールドの型

| Go の型 | ヘルパー |
|---|---|
| `~string` | `KeyString` |
| `~bool` | `KeyBool` |
| 符号付き整数の全幅、named type を含む | `KeyInt` |
| 符号なし整数の全幅 | `KeyUint` |
| `~float32`, `~float64` | `KeyFloat` |
| `[]byte` | `KeyBytes` |
| `time.Time` | `KeyTime` |
| 上記へのポインタ | `KeyOptional` |
| 上記のスライス | `KeyArray` |

ポインタとスライスは入れ子にできるので、`*time.Time` も `[][]int` も通ります。

フレーミングを持たない型（構造体、map、チャネル）は生成エラーであり、スキップされる
フィールドではありません。スキップされるフィールドこそ、このパッケージが取り除く静
かな誤答そのものです。導出元のフィールドをキーにしてください。

## 生成が保証すること

保証するもの:

- identity の prefix が必ず入るので、2 つのキー型が衝突しない
- すべての値が長さ前置されるので、連結は 1 通りにしか分解できない
- 手書きの `CacheKey` が黙って置き換えられることはない

依存集合が完全であることは保証しません。fetch にパラメータを足し、印を付け忘れれば、
キーは変わりません。その要求はどんなコンパイラにも見えない。生成が取り除くのは、
*正しい*依存集合のもとでも残る失敗のほうです。それは誤答系の 2 つで、残るのは、依存
を追加しているまさにその場所で目に入っている 1 つだけになります。

唯一これが捕まえるケース: キーとして渡された構造体に印が 1 つもなければ生成エラーで
す。identity だけのキーは、その型の全インスタンスに単一のエントリを与えてしまいます。

## 生成

型が発見される経路は 2 つです。

**tag による発見。** generate-all では、`cache` tag を持つ構造体にキーが生成されます。
`cache` tag のない構造体はキー型ではなく、そのまま放置されます。

**呼び出し箇所による発見。** framework がキーを読む呼び出しを登録します。キーは引数の
型です。

```go
calls := generator.NewCallRegistry()
err := calls.Register(generator.CacheKeyCall(
	generator.Function("example.com/framework", "Memo"),
	generator.ArgumentType("key", 1),
))
```

`GenericType` ではなく `ArgumentType` です。memo の呼び出しはキャッシュする結果につい
てジェネリックであり、キーはその隣にある値だからです。

生成を止めるには `cache-key` の feature flag を使います。

## 生成エラー

| メッセージ | 原因 |
|---|---|
| `marks no field` | キーとして渡されたのに印が 1 つもない |
| `has no cache key framing` | 構造体・map など、フレーミングを持たない型 |
| `already declares CacheKey` | 生成されるメソッドと衝突する手書きメソッド |
| `unknown cache tag option` | `key` 以外を書いた |
| `a blank field carries no value` | 空白の `_` フィールドに `cache` tag を付けた |
| `cannot be marked` | unexported または embedded なフィールドへの `cache:"key"` |

## フレーミングヘルパー

ヘルパーは公開されているので、生成が届かない場所では手書きもできます。すべての値は
バイト長、コロン、値の順で書かれます。

```go
cachekeybind.KeyString("abc")  // "3:abc"
cachekeybind.KeyInt(42)        // "2:42"
```

知っておく価値のある挙動が 2 つあります。

- `KeyOptional` は「不在」をあらゆる「存在する値」と区別します。nil ポインタとゼロ値
  へのポインタは別のキーになります。
- `KeyArray` は要素数を先に書くので、2 文字の要素 1 つと 1 文字の要素 2 つが衝突しま
  せん。nil スライスと空スライスは同じフレーミングになります。fetch への入力としては
  等しいからです。

これらは `htmlbind` のものではなく `cachekeybind` 自身のものです。コンポーネント出力
キャッシュは同じ規則で、しかし独自のセットでキーを組みます。2 つのキャッシュは identity
空間が別なので、キーが横断して比較されることはありません。
