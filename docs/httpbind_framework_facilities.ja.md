# フレームワーク向け機能一覧

これは tinybind を**土台にしてフレームワークを作る人**に対して tinybind が提供
するものの索引です。要件として整理してあります — 各機能が何のためにあり、何を要
求し、実装済みかどうか、そして仕様だけあって未実装のものは何か。

他のフレームワーク実装者向けガイドは作業単位で書かれています。ルーティングは
[httpbind_frameworkowner.ja.md](httpbind_frameworkowner.ja.md)、ページルータは
[httpbind_discovered_router.ja.md](httpbind_discovered_router.ja.md)、境界プロト
コルとクライアントランタイムは
[htmlbind_frameworkowner.ja.md](htmlbind_frameworkowner.ja.md) です。この文書だ
けは在庫表の形をしています。存在しない継ぎ目を迂回する前に、その継ぎ目が本当に無
いのかを確かめるために読んでください。

## ここに載る機能すべてが従う原則

継ぎ目を広げるのは、**既定の出力が 1 バイトも変わらず、契約が呼び出し側のまま**
であるときだけです。アプリケーション作者が書く側の形を動かす変更は拒否します。

方針はこれだけですが、はっきり書いておく価値のある帰結が 2 つあります。

**使わなければ無料。** ある機能をまったく使わないプロジェクトは、生成される Go も
書き出されるバイト列も一切変わりません。以下の項目はすべて、そう意図しただけでな
く実測で確認してあります。

**必要なものはモジュールが決め、どこから来るかは実装者が決める。** どのアセットが
必要か、どの head タグがマージされるか、どのクライアントランタイムが要るかは
tinybind が計算します。URL を決めることも、ファイルを配信することも、ヘッダを設定
することも、ルートを決めることもありません。

## markup の中のリクエスト固有値

> [!NOTE]
> **CSRF トークンはもうこれではありません。** ネイティブになるまではこの節の題材でし
> たが、今は unsafe form がすべて hidden field を自動で持ち、トークンは context では
> なく描画呼び出しの `htmlbind.WithCSRFToken(token)` で渡します。以下は CSRF *以外*
> のリクエスト固有の値には今もそのまま当てはまります。

### 問題

component は `http.Request` を受け取りません。`Fragment` は不変で、リクエストを
またいで再利用できます。つまり、リクエストに属する値 — リクエスト
ID、nonce、cookie の有無 — には自明な置き場所がありません。

パラメータ構造体を通す方法は動きますし、たいていのフレームワークが最初にやること
です。ただし代償が 2 つあります。値を必要とするページごとに、ハンドラから
`Params` を経てテンプレートへ渡す配線を繰り返すこと。そして値がただのテンプレート
変数になるため、「これを URL や属性やログ行に置いてはならない」という規則が、お願
いにしかならないことです。

### 実装されたもの: context を取る同期 external

`external async` の Go 実装は先頭に `context.Context` を宣言でき、`external live`
は必須です。2026-07-31 以降、素の `external` も宣言できるようになりました。

テンプレート側は何も変わりません。宣言はこれまでどおりです。

```
external RequestID(): string
external LocaleBanner(): html
```

選ぶのは Go を書く人であり、関数ごとに決められます。

```go
// トークンはリクエストのものなので render context を受け取る。
func RequestID(ctx context.Context) string {
	return tokenFrom(ctx)
}

// 受け取らない。呼ばれ方はこれまでと同一。
func SiteName() string { return "example" }
```

生成側がパッケージの Go ソースを読み、受け取る関数にだけ context を渡します。検出
は構文的です — パッケージがコンパイルされる前に走るため、パースできないファイルは
生成を失敗させずに読み飛ばされ、そのあと呼び出し形が合わなければ生成された呼び出
し位置で通常の Go のコンパイルエラーになります。

generator コマンド経由で生成しているなら自動です。コンパイラを直接呼ぶ場合は
`GenerateOptions.ContextExternals` で、async external 用にすでに渡しているものと同
じマップです。

```go
out, err := htmlbind.Generate("page.tb.html", source, htmlbind.GenerateOptions{
	ContextExternals: map[string]bool{"RequestID": true},
})
```

**値が markup なら文字列ではなく fragment を返してください。** `: html` と宣言し
た external は、エスケープされたテキストでも信頼された生バイト列でもなく、部分木
として描画されます。つまりフレームワークはトークンだけでなく hidden input 全体を
返せて、しかも通常の文脈チェックを通ります。

```
<form method="post">
  {LocaleBanner()}
  <input name="title" value="{title}">
</form>
```

```go
func LocaleBanner(ctx context.Context) htmlbind.Fragment {
	return banners.Locale(banners.LocaleParams{Tag: localeFrom(ctx)})
}
```

こちらの半分は今回より前から動いていました。欠けていたのは context だけです。

#### どの context が来るか

その render 自身の context です — async 系エントリの `ctx` 引数、あるいは同期系
エントリに `WithContext` で渡した値 — を、呼び出しが置かれた位置で読みます。await
や live の境界内の部分木では、それは境界の context です。したがって live の配信が
始めた仕事は、元の render ではなくその配信に紐づいて打ち切られます。

context を渡さなかった render にも context はあります。ですから、登録組み込み要素
の provider とは違い、context を取る external が context 不在で失敗することはあり
ません。

#### 生成コードへの影響

使わなければゼロです。そういう呼び出しを含むプラン命令は、クロージャの先頭引数と
して context を受け取り、名前もそれに合わせて変わります。

```go
// context を取る external が無い場合 — この機能が入る前と同一:
planPageOps.Text(func(p PageParams) string { return SiteName() }),

// ある場合:
planPageOps.TextCtx(func(ctx context.Context, p PageParams) string { return RequestID(ctx) }),
```

形は `TextCtx`、`RawCtx`、`AttrCtx`、`BoolAttrCtx`、`IfCtx`、`SlotCtx`、
`ComponentCtx`、そしてパッケージレベルの `ForCtx` です。選択は式ごとなので、両方
を混ぜたテンプレートは両方の形を出します。

#### 唯一拒否される位置

呼び出し側が開始した値を待つ場合 — `{await v = handles[Which()].count}` — の未設定
チェックは `Require` 命令に落ちます。これは、値を設定し忘れた呼び出し側がエラース
テータスを返せるように、何も書かれる前に走ることが存在理由です。外を呼べるチェッ
クはそれとは別物なので、ここで context を取る external を名指すのは位置を示した生
成エラーになります。

#### これは何ではないか

後述の登録組み込み要素の継ぎ目とは別物であり、その代わりにもなりません。external
は値をテンプレートに手渡すので、テンプレートはそれをどこにでも埋め込めます。組み込
み要素は値を描画するだけで、テンプレートのスコープには決して入れません。前者は安価
で汎用、後者は検査可能です。両方ほしいと言うフレームワークは、正しいことを求めてい
ます。

## ドキュメント head

component の head 宣言は、最初のボディバイトより前に単一のルート head へマージさ
れ、タグ単位で重複排除され、寄与ごとに宣言元の component が記録されます。そこは変
わっていません。変わったのは、**他に誰が寄与できるか**と、**寄与が何であり得るか**
です。

### 実装されたもの: render 呼び出しからの寄与

component は生成時に分かることを宣言します。呼び出し側はテンプレートに分からない
ことを知っています — たとえばページが今読み込んだレコードから取ったタイトルや、あ
る cookie が無いときだけ出すマーカーです。

```go
err := htmlbind.RenderChain(w, chain, page,
	htmlbind.WithHead(
		htmlbind.HeadTitle(order.Customer),
		htmlbind.HeadMeta(
			htmlbind.HeadAttr{Name: "name", Value: "description"},
			htmlbind.HeadAttr{Name: "content", Value: order.Summary},
		),
	),
)
```

ノードは 5 種類 — `HeadTitle`、`HeadMeta`、`HeadLink`、`HeadScript`、
`HeadNoScript` — で、いずれも markup ではなく値です。呼び出し側が文字列を渡して要
素を持ち込むことはできませんし、値は位置に応じてエスケープされます。

押さえておく性質が 4 つあります。

**head パスより厳密に前に到着します。** これは component の寄与がすでに満たしてい
る順序と同じなので、ストリーミングは何も変わらず、ボディのバイトはバッファされま
せん。

**最も内側の寄与としてマージされます。** component の寄与が先に来るので、呼び出し
側のタグはそれに依存できます。component がすでに宣言したタグが二重に書かれること
はありません。

**壊れたノードは最初の 1 バイトより前に失敗します。** レスポンスはまだエラーステー
タスを名乗れます。

**`HeadScript` は `src` を要求します。** アセットとは配信されている何かへの参照で
す。このパッケージのどの経路もインラインスクリプトを書かず、それが `script-src
'self'` を nonce 無しで維持できる理由です。

これは呼び出し側のための経路であって、バイトストリームへの差し込み口ではありませ
ん。ここで渡したものはテンプレートのスコープに入らず、component から読むこともでき
ません。作者のドキュメントシェルは作者のものであり続けます。

#### シェルの無いレスポンスでは

fragment レスポンスにはマージ先の head がありません。ブラウザで気づく代わりに、聞
いてください。

```go
tags, err := htmlbind.RenderHeadNodes(nodes)
```

render せずに同じ「書き出せる状態のタグ」が得られます。ナビゲーションのペイロード
に載せるのも、レスポンスを拒否するのも、意図して捨てるのも選べます。

### 実装されたもの: head 内の `noscript`

スクリプトを無効にしたブラウザはクローラではなく、そう名乗る `User-Agent` もありま
せん。そうしたクライアントをスクリプト不要の経路へ渡したいページが、適合する形で
それを言える場所は 1 つ — head 内の `noscript` によるリフレッシュです。

head 寄与はこれまで `link`、`meta`、`style`、`script`、`title` を受け付けていまし
た。`noscript` が、テンプレートで書ける集合と呼び出し側の集合の両方に加わりました。

```html
<head>
  <noscript><meta http-equiv="refresh" content="0; url=/_handoff"></noscript>
</head>
```

```go
htmlbind.WithHead(htmlbind.HeadNoScript(htmlbind.HeadMeta(
	htmlbind.HeadAttr{Name: "http-equiv", Value: "refresh"},
	htmlbind.HeadAttr{Name: "content", Value: "0; url=/_handoff"},
)))
```

子は `link`、`style`、`meta` だけです。それ以外はボディの内容です。要素の子を持て
る唯一の寄与要素で、他はすべて静的テキストしか受け付けません。

テンプレートに書く形は無条件です。常に出したいページには正しく、cookie が立ったら
止まるべき handoff には誤りです。その条件付きのケースこそ、上の呼び出し側経路の用
途です。

### 出所

`Head` と `HeadSources` は `Fragment` と `Wrapper` の両方にある並行リストです。ど
ちらの添字 *i* も同じタグを指し、出所は `ComponentName (file:line:col)` の形です。
配信できない寄与を拒否するときは、markup を印字する代わりに component を名指してく
ださい。

## アセット

component の `<style>` はスコープ化されて head へ持ち上がり、component の
`<script>` は内容ハッシュ付きファイルへ抽出されてマージ済み head から参照されます。
どちらも `PublicDir` の下に書かれ、`PublicURLBase` の下で参照され、どちらも決定的
です。入力が同じなら名前もバイト列も同じものが再生成されます。

配信するのは実装者です。tinybind は静的ファイルサーバを持たないので、生成アセット
ディレクトリ全体に対する 1 ルートだけが手作業になります。

対象は、コンパイル中の生成単位のテンプレートファイルで宣言された component です。
**ライブラリ**が供給する component は対象外です — 次節を見てください。

## 仕様はあるが未実装のもの

設計と合意は済んでいて、実装がまだのものです。待つか迂回するかを判断できるよう、
それぞれ何を与えるはずかを添えます。

### 登録組み込み要素（builtin element）

フレームワークが実装する markup を、生成単位のどのテンプレートからも、import も
ページごとの宣言も無しに名前で呼べるようにするものです。

```html
<csrf-token />
<pw-noscript-handoff />
```

**これは component ではありません。** この区別は語法のこだわりではなく、実体が違い
ます。`component` は PascalCase で、テンプレートファイルに宣言され、ファイルをまた
ぐときは契約を書き直す `external` 宣言経由で参照します。組み込み要素は kebab-case
で、generate コマンドに登録され、生成単位全体でどこからでも使え、独立した component
にはならず、それを含む component のプラン命令へ落とし込まれます。他所で
*framework-provided components* と呼ばれているのを見たなら、それは同じ継ぎ目をフ
レームワーク側から自然に読める名前で呼んだものです。

ハイフンがこの空間を空けています。`rule:template-name-casing` は実在の HTML 要素に
kebab-case を割り当てており、ハイフンは HTML のカスタム要素マーカーです。つまり素の
`csrf-token` はカスタム要素の空間に入るので、標準要素と衝突しません。

登録は generate コマンドに渡すホワイトリスト — 名前から Go シンボルへの静的なマッ
プで、リフレクションも init 順序も要りません — なので、何も登録しないプロジェクト
は今と同じものを生成します。リクエスト固有の値を持たない要素は完全に静的バイト列に
畳まれ、レンダー時のコストはゼロです。値を持つものは、そのプラン位置で context を
取る provider 関数を呼びます。

ホワイトリストにはもう 1 種類のエントリがあります。素通し（passthrough）の名前ある
いはグロブパターンで、アプリケーションが使う Web Components を列挙できます — ライ
ブラリ丸ごとなら `sl-*` — これらはそのまま出力されます。これが無いと、ハイフン空間
を登録名だけに閉じた時点で Web Components が一律禁止になってしまいます。

この方法でしか得られない性質が 3 つあり、これが「external の糖衣ではない」理由です。

- **値がテンプレートのスコープに入らない。** 要素がトークンを描画します。
  external はテンプレートに手渡します。
- **配置を検査できる。** head 専用の寄与をボディに書けば、半分だけ動くページではな
  く生成エラーになります。
- **依存が宣言される。** cookie を読む要素は、レスポンス全体をその cookie に依存さ
  せます。宣言された vary 軸があってはじめて、どのテンプレートにも書かれていないも
  のに対して `Vary` ヘッダを組み立てられ、出力キャッシュが「キーにできないものは保
  存しない」と判断できます。

### component アセット

こちらは本当に *component* の話です — 日付ピッカー、チャート、ソート可能な表。テン
プレートファイルに書かれた PascalCase の宣言と、その隣にあるスクリプトです。上の行
とは主体が違います。上はフレームワークが Go で実装した要素を登録する話でした。継ぎ
目としては両方を支える必要があります。組み込み要素もスクリプトを必要とし得るからで
す。ただし今日まったく答えが無いのはライブラリのほうです。

component ライブラリとは、テンプレートとスクリプトといくらかの Go です。このうち
2 つには置き場所があります。ライブラリはルートもスキャフォールドもシェルも持たない
ので、フレームワークが自分のランタイムを参照するようには自分のファイルを参照できま
せん。そもそもパッケージをまたいで到達できる必要もあり、`external` 宣言が何を指せ
るのかは未解決のままです。

追加されるはずのもの:

- **埋め込みアセット表** — バイト列、ダイジェスト、メディアタイプを生成 Go として
  出力し、実行時にファイルシステムを読まないようにする。TinyGo や wasm ターゲット
  ではファイルシステムが無いこともあるため、これが要ります。
- **静的に分かる必要アセット集合** — `HasAwaitBlock` と同じようにチェーンを畳んで
  求められるもの。後の配信が必要とし得るスクリプトをドキュメントが最初から抱えられ
  るので、入れ替えの最中に取りに行く必要がなくなります。
- **呼び出し側が供給する URL 関数** — マウントパスもキャッシュ方針も、メモリから配
  るのかディスクから配るのかも、実装者しか知らないという既存のパターンの一般化。

これにダイジェストによる重複排除、登録順に依存しない順序、そしてどこにもインライン
配信が無いことが伴います。

2 番目が最も重要で、最も難しい項目です。live の配信や fragment の入れ替えは、最初
のレンダーに無かったスクリプトを必要とする component を差し込めます。必要集合がレ
ンダー中にしか分からないなら、入れ替え時にスクリプトを読み込むしかなく、それはこの
モジュールが意図的に持たないクライアント設計です。

### レンダー時のスクリプト寄与

登録済みスクリプトを名前でレスポンス単位に選ぶものです。外部 URL のケースは、当面
は上の head 経路で足ります — `src` 付きの `HeadScript` は、今日すでにレスポンス単
位の script タグです。欠けているのは、生成側がすでにハッシュしてファイルに書き出し
た寄与を名前で指せるレジストリのほうです。

## 全体で維持している制約

- **エスケープは変わりません。** リクエストを読んでも、値の書かれ方は何も変わりま
  せん。context を取る external の結果も、他のあらゆる式と同じように位置に応じてエ
  スケープされます。
- **どこにもインラインスクリプトはありません。** 抽出も寄与も呼び出し側のノードも、
  インラインの script ブロックを出しません。
- **クローキングはしません。** リクエストを読んで決めるのは**配信**であって、内容
  ではありません。モードヘッダはテンプレートのスコープに届かず、テンプレートはそれ
  で分岐できません。
- **リフレクション無し、実行時のファイルシステム読み取り無し、init 順序依存無し。**
  TinyGo と wasm ターゲットは維持されます。
- **`htmlbind` は `net/http` に依存しません。** レンダリング側はトランスポートにつ
  いて意見を持たず、ここに挙げたどの機能でも持ちませんでした。

## 不足を報告するには

このリポジトリの `.knowledge` カタログに、下流からの要望が 3 ラウンド分記録されて
います — 生成の継ぎ目、live 統合、そしてこの文書の実装済み項目が出てきた component
の継ぎ目です。各ラウンドは受理の前にリリース済みソースに対して検証され、受け入れた
ものと並べて、拒否したものとその理由も記録されています。

最も役に立つ報告は、継ぎ目だけでなく**その継ぎ目にぶつかった機能**を名指すもので
す。直近のラウンドで挙がった 4 つの要望のうち 2 つは、このカタログがすでに持ってい
た設計でした。それを動かしたのは、あるフレームワークが 1 週間のあいだに 3 つの機能
からそこへ辿り着いた、という事実のほうです。
