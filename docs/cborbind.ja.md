# cborbind ガイド

`cborbind` は、エンコード・デコードする型の CBOR コーデックを生成します。宣言を書
く必要はなく、「コーデックをください」と頼む構文もありません。**エントリポイント
を呼ぶことが依頼そのもの**です。

```go
buf = cborbind.AppendCBORInArrayTo(buf[:0], input)
input, err := cborbind.DecodeCBORInArrayFrom[PlayerInput](buf)
```

ジェネレータがこの呼び出しを読み、コーデックを書き、対応するメソッドを型に付けま
す。呼び出しを追加した直後の1回目のビルドは通りません(メソッドがまだ存在しないた
め)。ジェネレータを走らせてからビルドし直してください。これは他の生成モードと同
じブートストラップで、その代わりに「コーデックが無い」が実行時の事故ではなく**コ
ンパイルエラー**になります。

## 名前がコンテナを決める

構造体は CBOR の配列かマップのどちらかとしてエンコードされます。方向ごとにエント
リポイントが2つあるのは、この2つが「オプション違い」ではなく**別の契約**だからで
す。

| | 配列 | マップ |
| --- | --- | --- |
| ワイヤ上 | 位置ベース、メンバ名なし | テキストキー、RFC 8949 bytewise 順 |
| 未知のメンバ | 存在しえない | デコード時にスキップ |
| フィールド追加 | 両端を同時に再ビルド | 古いビルドも読み続けられる |
| サイズ | 小さい | キー名の分だけ大きい |

```go
cborbind.AppendCBORInArrayTo(dst, v)          // 配列
cborbind.AppendCBORInMapTo(dst, v)            // マップ
cborbind.DecodeCBORInArrayFrom[T](data)       // 配列
cborbind.DecodeCBORInMapFrom[T](data)         // マップ
```

配列形状で生成された型に対してマップのエントリポイントを呼ぶと**コンパイルが通り
ません**。制約を形状ごとに分けているのは意図的で、もし両形状が1つのメソッドを共有
していたら、その呼び出しはビルドが通ったうえで**黙って別形状のバイト列を吐きま
す**。

## どちらを選ぶか

判断は1つの問いだけです。**両端を同時に更新できますか？**

できるなら配列を選んでください。一緒にリリースするゲームクライアントとサーバ、ま
とめてデプロイする2プロセスなどです。ネストした構造体を含む3フィールドのメッセー
ジで6バイトです。

できないならマップです。保存されるスナップショット、キューのペイロード、古いビル
ドが読む可能性のあるもの。キー名のコストを払う代わりに、リリースを調整せずにフィ
ールドを追加できます。

## 生成されるもの

`AppendCBORInArrayTo(dst, PlayerInput{})` に対して生成されるのは:

```go
func appendPlayerInputCBORArray(dst []byte, v PlayerInput) []byte
func (v PlayerInput) AppendCBORInArrayTo(dst []byte) []byte
func (v PlayerInput) AppendCBORTo(dst []byte) []byte   // 委譲
```

3つ目はドライバの `cbor.Appender` そのものなので、そのインターフェースを持つ利用
者は cborbind を知らなくてもあなたの型を扱えます。デコード側も
`DecodeCBORInArrayFrom` と `cbor.Decodable` で対称です。

メンバ名は `json` タグから取ります。JSON コーデックと同じ名前なので、構造体はワイ
ヤ名を一度書けば済みます。

登録は一切行わず `init` も生成しません。ディスパッチは生成時に解決されるので、メ
ッセージごとのルックアップはありません。

## 方向

方向は「どちらのエントリポイントを呼んだか」で決まります。append しかしないパッケ
ージにはデコーダが生成されません。ルートでも、その下のどの構造体でも同じです。wasm
クライアントでは、使われないデコーダはそのままバイナリサイズです。

## 1つの型に両方の形状

メソッド名が衝突しないので、1つの型が両形状を持てます。

```go
cborbind.AppendCBORInArrayTo(dst, t)   // 一緒に出荷するピア向け
cborbind.AppendCBORInMapTo(dst, t)     // 自分より長生きするログ向け
```

この型には委譲用の `AppendCBORTo` は生成されません。委譲先が一意に決まらないから
で、宣言順で勝手に決めるより、曖昧さが型に見えている方がましです。

## 扱えるフィールド型

`string`、`bool`、`float64`、すべての固定幅整数(`int8`〜`uint64`、`int`、`uint`)、
ネストした構造体、それらのスライス、`map[string]…`。名前付き型も使え、両方向で変
換されます。

それ以外は型名とフィールド名を挙げた生成エラーになります。`payload:"*"` の rest
map、独自の JSON コーデックだけを持つフィールド、アップロードファイルは、黙って落
とすのではなく拒否します。

## プロファイルはありません

オプションも CLI フラグも制限用の構造体もありません。コーデックが**扱える**型はジ
ェネレータの能力であり、実際に**扱う**型はあなたの構造体の性質です。プロトコルに
float を入れたくないなら `float64` フィールドを宣言しない。それが同じ主張を、既に
それを担っている場所で言うということです。

## 生成

```bash
tinybind-gen generate -dir .
```

エントリポイントを一度も呼ばないパッケージは CBOR を一切出力せず、CBOR 実装をリン
クもしません。`cborbind` 自体は何も import しません。インターフェースがバイトスラ
イスだけで書かれているので、ドライバを名指しするのは生成コードだけです。

生成されたコーデックは TinyGo の `wasm` と `wasip1` でビルドでき、動作します。

## HTTP の CBOR モードとの関係

`-cbor-http` は別物です。あちらは全ルートに `application/cbor` を受け付けさせ・返
させるもので、型ごとの呼び出しではなくプロジェクト単位のオプションです。両立しま
す。両方で使われる型はキーイングごとに1つずつコーデックを持ち、どちらも同じ `json`
タグを読むのでメンバ名は必ず一致します。ネゴシエーションについては
[httpbind.ja.md](httpbind.ja.md) を参照してください。
