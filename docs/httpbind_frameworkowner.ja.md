# httpbind フレームワーク実装者向けガイド

このガイドは、tinybind の**上に**ウェブフレームワークを作る人のためのものである。
扱うのはルーティング —— ルートがどうやって登録済みハンドラになるか、それぞれの
やり方で生成が何を見られるか、どこから先が実装者の責務か。

言語仕様と通常のアプリケーション利用は [httpbind.ja.md](httpbind.ja.md) を先に
読むこと。探索型ルータには専用のガイド
[httpbind_discovered_router.ja.md](httpbind_discovered_router.ja.md) があり、
ページの形、セグメント記法、レイアウト、サーバーアクション、生成される出力を
そこで扱う。描画側 —— 境界プロトコル、クライアントランタイム、head のマージ ——
は [htmlbind_frameworkowner.ja.md](htmlbind_frameworkowner.ja.md) にある。
ここではどれも繰り返さない。

## 2つのルータ —— 汎用と特化

tinybind にはハンドラを `ServeMux` に載せる方法が2つある。同じ機能の2つのスタイル
ではないし、API とページの住み分けでもない。

**登録型ルータ**は昔ながらの標準的な Go のやり方であり、天井が無い。登録は実装者
が書き、ハンドラは好きなものを書き出す —— JSON でも HTML でもファイルでもストリーム
でも。生成は登録を読んで、そのハンドラが何をバインドし何を返すかを知る。

```go
mux.HandleFunc("POST /users/{id}", updateUser)
```

API 専用の性質は何ひとつ無い。API は単に、生成される OpenAPI が元を取るケースと
いうだけだ。登録型ルートから HTML を返すのはごく普通のことで、きちんとサポート
されている。長いあいだ、このリポジトリではそれが唯一のやり方でもあった。

**探索型ルータ**は、その汎用性を1つの形と引き換えにする。人が URL を辿ると、
テンプレートとそのレイアウトから描画されたページが返る。だからトラフィックは
`GET` になり、入力は URL が運ぶものだけになる。ディレクトリを作れば、生成が登録を
書く。

```
pages/users/id_/page.tb.html    → GET /users/{id}
```

その形の内側にいるかぎり、歩いて登録するループを書かなくてよい。外に出れば
登録型に戻る。これは代替手段というより、すべてが立っている土台である。

この適用範囲の違いが、それぞれが流れる向きを決める。汎用ルータは Go のコードに
よって定義されるので、Go のソースが真実で生成はそれを読む。ページのルータは
ページによって定義されるので、ファイルシステムが真実で生成が Go を書く。

| | 登録型ルータ | 探索型ルータ |
| --- | --- | --- |
| 適用範囲 | `net/http` が返せるものすべて | テンプレートから描画される `GET` ページと、そのサーバーアクション |
| メソッド | 任意 | ページは `GET`、アクションは `POST` |
| レスポンス | ハンドラが書いたもの | 描画されたページ（ハンドラの段を取らないかぎり） |
| ハンドラの入力源 | パス、クエリ、ヘッダ、Cookie、ボディ、multipart | ページはパスとクエリ、アクションは任意 |
| ルートを定義するもの | Go ソース中の登録呼び出し | `page.tb.html` を持つディレクトリ |
| ハンドラを書く人 | 常に実装者 | ページは生成、アクションは実装者 |
| 生成されるもの | リクエスト/レスポンスのバインディング、OpenAPI | コンポーネント、デコーダ、`ServeMux` |
| `mux.HandleFunc` を呼ぶ人 | 実装者 | 生成された `Register` |
| OpenAPI | 出る | 設計として出ない |
| 1回の実行の単位 | 1パッケージディレクトリ | 1ルートツリー |
| 設定の接合部 | `Options` の呼び出しパターン | `Emitter` のテンプレートとシンボル |
| 生成が失敗する条件 | パターンがコンパイル時定数でない | ディレクトリ名が正当な import パス要素でない |

この表の2行は同じ事実を2度見ているにすぎない。`GET` にボディは無いので、パスと
クエリが**ページ**の持ちうる入力面のすべてになる。ページが `Bind` のタグ語彙を
まったく必要とせず、入力が構造体ではなく普通の Go の引数である理由もそこにある。
サーバーアクションはその形のもう半分だ。ボディを読み、そして実装者が書く普通の
ハンドラである。変更操作が返さなければならないものを、固定の型付き戻り値では
覆えないからにほかならない。

実務上の差はむしろ最後の行である。登録型は評価できない式に敗け、探索型は Go が
受け付けないディレクトリ名に敗ける。どちらの失敗も黙って起きることはない。

2つのルータは交渉せずに1つの mux を共有する。

```go
mux := http.NewServeMux()
mux.HandleFunc("POST /api/users/{id}", updateUser)   // 登録型: 自分の JSON API
pages.Register(mux)                                   // 探索型: ページとアクション
```

`Register` は mux を自分で作ると主張せず既にあるものを受け取る。そこから先は
素の `ServeMux` の挙動である。登録順は関係ない。生成された `/{$}`
のルートは手で登録した `/api/` のサブツリーに手を出さず、未マッチのパスは 404 の
まま、`GET` しか無いページへの `POST` は 405 のままである。

衝突が1つだけ現実にある。同じメソッドとパスを2回登録すると panic する。
`ServeMux` が重複パターンに対してそうするからだ。手書きのルートが生成されたルート
を覆うと、黙って上書きされるのではなく起動時にクラッシュする —— 望ましい失敗方だが、
同時に、そのパターンを既に手で登録しているサーバーにページを1つ足すと壊れうる、
ということでもある。

## 登録型ルータ

生成はルート登録を読んで3つのことを知る。パターン、ハンドラ、そしてそのハンドラが
バインドし書き出す型。そこからバインディングコードと OpenAPI ドキュメントを作る。
登録そのものは決して生成しない。

### 自分の API を教える

フレームワークが `http.ServeMux` と `httpbind.Bind` をそのまま露出することは
まれである。呼び出しレジストリは、探索が実装者のラッパーに一致するために存在する。

```go
calls := generator.NewCallRegistry()
if err := calls.Register(generator.RequestBindCall(
	generator.Function("example.com/framework", "Parse"),
	generator.GenericType("request", 0),
)); err != nil {
	return err
}
options, err := calls.Options(generator.DefaultOptions())
```

`Options` はルート側も持つ。`ServeMuxes` は `Handle` と `HandleFunc` を登録と
みなす型を、`RouteMethods` は別名のメソッドを持つ mux を、`RouteFunctions` は
パッケージレベルの登録関数を指定する。いずれも権威的な集合であり、設定すると
組み込みの識別子は**拡張ではなく置換**される。標準のものも欲しいときに
`DefaultOptions` を土台にするのはそのためだ。

同一性は名前ではなく `go/types` で解決される。設定していない型の `HandleFunc`
という名前のメソッドは登録ではない。無関係な API がルーティングと誤認されない
のはこの性質による。

### 見えないもの

探索は静的でパッケージ内に閉じており、推測せずにその旨を報告する。

```go
mux.HandleFunc("GET " + prefix, handler)   // コンパイル時定数でない
for _, r := range routes {                  // 反復ごとのパターンが不明
	mux.HandleFunc(r.Pattern, r.Handler)
}
otherPackage.RegisterRoutes(mux)            // ハンドラの葉が別パッケージ
```

いずれもファイル・行・理由を名指しする診断を出し、該当ルートは誤った内容で
文書化されるのではなく OpenAPI から省かれる。CI では `-check` を付けて、これらの
診断でビルドを落とすこと。

パッケージ内に閉じるという規則は、見た目以上にフレームワーク設計を規定する。
1回の実行がハンドラを別パッケージまで追わない以上、登録とその指すハンドラは
通常同居すべきである。2つのディレクトリは2つのプロセスであり、生成時に導出する
識別子が実行ごとのカウンタに依存してはならない、ということでもある。

## まだ無いもの

- 登録型は、動的・ループ・パッケージ外の登録を、すべて診断するのではなく依然
  として無視する。
- 探索型が登録するのは `GET` のページルートと `POST` のサーバーアクション
  エンドポイントである。その形の外にあるもの —— 別のメソッド、描画されたページ
  でないレスポンス —— は登録型ルートのままであり、それが本来の居場所である。
- `server-action` はルートツリーの中でしか使えない。テンプレート側はモードに
  依存しないので、欠けているのはフラットモードのテンプレートに対してハンドラを
  URL に解決する仕組みだけである。素直な実装は、上で述べた登録探索からパターンを
  読むことになる。

探索型ルータには専用の一覧が
[httpbind_discovered_router.ja.md](httpbind_discovered_router.ja.md) にある。
