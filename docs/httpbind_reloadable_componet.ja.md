# リロード可能な component 利用ガイド

リロード可能な component とは、描画された領域をブラウザ自身が更新できる `htmlbind` の component です。ページの入力が変わると、サーバはレンダリングをやり直し、各領域をブラウザが既に持っているものと突き合わせ、**実際にマークアップが変わった領域だけ**を返します。

1つの URL が3通りに応答します。更新用ヘッダが無ければ従来通りの完全な HTML なので、ランタイムを持たないブラウザ、クローラ、`curl` から見える内容は変わりません。ヘッダがあれば、同じ URL がページ遷移の差分、あるいは単一 component の再描画を返します。

考え方は「検索パラメータを引数に取る page component」と同じです。ページはリクエストの関数であり、引数を1つ変えただけでページ全体を読み直す必要はない、ということです。

> [!IMPORTANT]
> この機能はマイルストーンに分けて提供されます。以下は完成形の挙動で、現時点で動く範囲は「[提供状況](#提供状況)」を参照してください。既存テンプレートの描画結果は変わりません。更新機能は、それを要求したリクエストに対してのみ有効になります。

## 自動化されること

- 構成中の各 layout と page を更新境界として扱うこと
- 各境界のルート要素への安定した instance 識別子の付与
- component の宣言済み入力の正規化ダイジェスト計算
- 子を除いた、境界自身のマークアップのダイジェスト計算
- 新しいレンダリング結果と、ブラウザが送り返したダイジェストとの比較
- 変更された最上位の境界の選択と、それだけの送信
- リクエストヘッダ1本による document / navigation モードの判定
- 登録された component の再描画エンドポイントの公開
- 結果を適用するブラウザランタイムの配信
- 解釈できないものに遭遇した際の、通常のページ遷移へのフォールバック

ハッシュの計算、ID の採番、更新エンドポイントの実装は不要です。ハンドラは従来と同じチェインを描画するだけです。

## ユーザーが用意するもの

1. `.tb.html` component の構成（ドキュメントシェル、layout、page）
2. そのチェインを `htmlupdate` 経由で描画するハンドラ
3. validator 用の鍵
4. ブラウザランタイムを配信するルートと、それを読み込む script タグ
5. 更新を要求するブラウザ側コード、またはランタイムが傍受するリンク
6. 再描画したいインスタンスへの DOM `id` と、その component 内の認可チェック

## 差分が起きるまで

```text
初回        GET /search?q=go
            -> 完全な HTML。各境界が data-tb-id を持つ

更新        GET /search?q=rust
            X-Tinybind-Render: navigation;v=1
            X-Tinybind-Manifest: c1:8Qv…,c2:Lm4…
            -> { ops: [ c2 を <p …>results for rust</p> に置換 ],
                 manifest: [ c1:8Qv…, c2:Nk9… ] }

適用        ランタイムがその1要素だけを差し替え、新しいダイジェストを保持する
```

layout のマークアップは2回目に流れません。ダイジェストが変わっていないので、ブラウザが既に持っているとサーバが判断できるためです。

## 更新境界

描画されるチェイン中の layout と page は、**自動的に**すべて境界になります。宣言は不要です。layout チェインは部分更新が求める構造そのもの、つまり「たいてい生き残る外枠が、たいてい変化する内側を包む」形だからです。

通常の component 呼び出しは境界に**なりません**。この線引きが無いと、500行のリストが毎リクエスト500件のエントリを載せることになります。任意の component を境界にするのは明示的なオプトインで、対象は export された component に限られます。境界になるということは識別子が DOM とプロトコルに出るということなので、ファイル内の実装詳細が外から名指しできてはいけないからです。

ドキュメントシェルは境界になりません。部分更新は既存のドキュメントを再利用するので、シェルを置き換えては意味がありません。

### 単一ルート要素の制約

境界はルート要素をちょうど1つ描画する必要があります。識別子がその要素の属性に載り、すべての操作がそのノードを対象にするためです。

これは**ラッパーを足せという意味ではありません**。ルートが `<tr>` のテーブル行 component は問題なく、兄弟の `<tr>` を2つ返す component が引っかかります。doctype、コメント、空白、巻き上げられる `head` 宣言は数に含めません。

境界が自動である間は、この条件を満たせない component は単に境界にならないだけで、コンパイルは通ります。境界が明示指定になった段階で、満たせないオプトインは生成時エラーになります。

## 2つのダイジェスト、2つの役割

境界は2つのダイジェストを持ちます。この違いが重要です。

**input validator** は component の宣言済みパラメータを正規化してエンコードし、生成コードのバージョンを添えたものです。キャッシュ鍵であり、診断の手掛かりです。

**frame validator** は境界自身の描画バイト列で、**入れ子になった境界の出力は除外**します。境界を省略してよいかの判断はこちらが担います。

2つある理由は、**入力が同じでも出力が同じとは限らない**からです。component は時刻、データベース、ロケール、リクエストを読み得ます。出力キャッシュを明示的に有効にした component だけが入力一致で描画を省略でき、それ以外の境界は描画してから比較します。**差分が省くのは送信であって、実行ではありません。**

frame から子を除くことが、layout の再利用を成立させます。page のパラメータを変えても layout 自身のマークアップは同じハッシュになるので、layout は DOM に残ったまま子だけが差し替わります。

ダイジェストは利用者が渡す秘密鍵で keyed 化されます。鍵なしのハッシュだと、エントロピーの低い内容について「推測したものと突き合わせて一致を確認する」ことができてしまいます。鍵のローテーションは何も壊しません。比較が外れるので、次の応答が完全なレンダリングになるだけです。

## レンダリングモード

| モード | 契機 | 応答 |
| --- | --- | --- |
| document | 更新ヘッダなし | 完全な HTML |
| navigation | `X-Tinybind-Render: navigation;v=N` | 対象ルートの変更された境界 |
| redraw | `GET <prefix>/redraw/<kind>/<id>?args` | その component のサブツリー |
| live 配信 | 2本目の接続での `X-Tinybind-Render: navigation;v=N` | 開いたままの配信レコードストリーム |

最後の行は別機能で、この交渉を共有するため参考として並べています。[live source](htmlbind.ja.md#live-sources) はドキュメント描画の時点でその場に確定するので、ドキュメントのレスポンス自体は完了します。そのあとランタイムが2本目の接続を開き、ソースが値を出し続けるあいだ配信を運びます。この接続が切れると（プロキシのタイムアウト、スリープなど）領域は何の合図もなく凍結してしまうので、ランタイムが開き直します。再接続は同じ要求をもう一度出すだけです。

この接続は現状 navigation トークンで流れています。専用の `live;v=N` トークンは設計はありますが未実装で、送る側も解釈する側も存在しません。これを前提に実装しないでください。

この再開が異例に安く済むのには構造的な理由があります。**live の各配信は差分ではなく領域の状態全体を運ぶ**ためです。取りこぼした値には価値が無いので、カーソルもイベントログも再送も、`Last-Event-ID` に相当するものも要りません。境界 ID は位置から割り当てられるので、描画し直せば画面上に既にある ID が再現されます。再接続した領域はプレースホルダを挟まず、現在の状態をそのまま描きます。

`Accept` を使わないのは意図的です。共有キャッシュは `Vary: Accept` を正規化したり落としたりしますし、1つの URL は1つのキャッシュ可能なドキュメントリソースであるべきだからです。クエリパラメータも同様に避けています。正規 URL、共有される URL、ログに残る URL が変わってしまいます。

すべての応答が更新ヘッダに対して `Vary` します。差分応答はドキュメント固有の validator を含むため `no-store` です。

解釈できないもの（未知のモード、サーバが話せないバージョン、切り詰められたヘッダ、プロキシが落としたヘッダ）は、エラーではなく**完全なドキュメント**になります。この規則があるからこそ、各マイルストーンは未完成のままでも不正にはなりません。

## プロトコルバージョン

バージョンが指すのはワイヤ上の契約です。属性名、マニフェストのフィールド、operation の種類、validator の構成方法。フレームワークが所有する単一の整数で、プロジェクト設定ではなく、すべてのダイジェストに混ぜ込まれます。

**テンプレートは指しません**。テンプレートを編集すると、その component のバージョンが validator の中で変わります。プロトコル番号は動きません。

クライアントとサーバは完全一致が必要です。不一致は完全なドキュメントを返し、これがローリングデプロイを安全にします。旧バージョンが描画したページの次のリクエストが新サーバに届く状況は必ず起きるからです。

## 差分の操作

差分は**変更された最上位の境界だけ**を運びます。置換される境界の子孫はその置換 HTML に既に含まれているので、重ねて送れば存在しないノードを狙うことになります。

- `replace` — 境界の要素を新しいマークアップに差し替える
- `insert` / `remove` / `move` — キー付きリストにおける構造変化
- 穴あき `replace` — 祖先を置換しつつ、変化していない子孫を移し替えて DOM 状態を保つ

応答は head 操作も運びます。初めて登場する component はまだライブの head に無いスタイルシートやスクリプトの link を伴い、それらが設置される前にマークアップを適用すると領域が無スタイルで一瞬表示されてしまいます。読み込みに失敗したスタイルシートが更新を無限に止めることはありません。

## クライアント API

```js
await tinybind.update("/search?q=rust");   // 現在のルートを再描画
await tinybind.navigate("/guides/intro");  // 別ルートへ移動
await tinybind.redraw("card-1", { page: 2 }); // component 1つを再描画
await tinybind.apply(response);            // 操作の応答を適用
```

`tinybind` は既定の名前であって固定の名前ではありません。`GlobalName` で変更できるので、このモジュールの上に立つフレームワークは、依存先の名前ではなく自分の名前を利用者に見せられます。ランタイムを自分のアセットに統合する場合は、スクリプトをもう1本読むのではなく `createPartialUpdateRuntime(config)` を呼びます。

同一オリジンについては、リンクと GET フォームを傍受します。要素かその祖先に `data-tb-ignore` を付けるとブラウザに戻せます。この属性も他と同じく設定した接頭辞に従うので、`pw` を使うプロジェクトでは `data-pw-ignore` になります。修飾キー付きクリック、`target`、`download`、クロスオリジン URL もブラウザに任せます。フォームのフィールドはそのままクエリになるので、検索フォームは同じページを絞り込む形になり、送信のたびに履歴を積まず URL を置換します。非 GET の送信は傍受しないので、post-redirect-get はそのまま動きます。

`subscribe` は `start`・`applied`・`superseded`・`fellBack`・`redrawn` を配信します。運ぶのは結果であって component の引数ではありません。進捗表示、計測、領域が置換された後に再初期化が要るサードパーティ製ウィジェットには十分です。購読側が例外を投げても、監視対象の更新は壊れません。

履歴・スクロール・フォーカスは実際のページ遷移と同じように振る舞います。URL は応答が確定してから push するので、差分が失敗しても履歴は汚れません。戻る/進むではスクロール位置を復元し、フォーカスは維持するか、黙って失うのではなく定められたランドマークへ移します。

失敗経路（ネットワークエラー、タイムアウト、差分でない応答、プロトコル不一致）はすべて、同じ URL への通常のページ遷移を行います。**ユーザーの操作が失われることはありません。**

JavaScript が無い環境では、リンクもフォームも従来通りに動きます。

## component 単体の再描画

ページ遷移差分が答えるのは「このページで何が変わったか」です。再描画が答えるのは別の問いで、「この領域を、この値で描き直せ」です。ここまでの仕組みは一切使いません。マニフェストも validator も比較もありません。

component を reloadable と宣言し、呼び出し側でインスタンスに通常の DOM `id` を与えて、呼びます。

```text
export reloadable component UserCard(id: string, userId: int): html {
<article class="card">…</article>
}
```

```text
<UserCard id="card-1" userId={current.ID} />
```

宣言から型付きのクエリデコーダと登録値が生成されます。設置はアプリが行うので、公開はテンプレート側だけでなく Go 側からも見えます。

```go
registry := &htmlupdate.Registry{}
if err := registry.Register(pages.UserCardReloadable); err != nil {
    return err // kind の重複。本番で見つけてよいものではありません
}
options.Mount(mux, registry)
```

kind が重複した登録は失敗します。kind が覆うのは component の名前・引数・マークアップであってパッケージではないので、黙って後勝ちにすると、見た目は同じでも別パッケージの external を呼ぶ component が応答してしまうからです。ここで panic せず error を返すのは、起動時の検証をまとめて行う呼び出し側が、最初の1件で止まらず全部を報告できるようにするためです。返す先がない呼び出し側のために `MustRegister` もあります。

`Mount` は `Handle(string, http.Handler)` を持つ任意のルータを受け取るので、フレームワークは自前の mux にまとめて登録できます。

`id` パラメータは必須で、クエリではなくパスから埋まります。フレームワークはこの id と component の kind を**毎回のレンダリングで**ルート要素に書き出すので、再描画で置換された後も領域は名指しでき、再描画し続けられます。reloadable な component は export 済みかつ単一ルートである必要があり、それ以外のパラメータはクエリ文字列が決定的に運べる型に限られます（record、配列、`html` は生成時に拒否）。自動境界と違いこれらはエラーです。作者がエンドポイントを求めたのだから。

```js
await tinybind.redraw("card-1", { userId: 42 });
```

これがそのまま GET になります。

```text
GET /_tb/redraw/UserCard@8Qv3n1/card-1?userId=42
```

サーバは**その component だけ**をクエリ文字列の引数で実行し、同じ `id` を持つ単一ルート要素としてサブツリーを返します。復元するものが無いので、capability トークンも署名鍵もページ実行も不要です。

`id` はフレームワークのものではなく利用者のものです。領域を再読み込みするのは意図的な行為なので、名前も意図的に付けるべきですし、`getElementById` が既に解決手段を持っています。component の内部ではなく**呼び出し側**に書いてください。内部に書くと全インスタンスが同じ id になります。ループ内では、元々そうするようにアイテムのキーから組み立てます。

component 名の後ろのセグメントは、パラメータとコンパイル済みマークアップのハッシュです。役割は**バージョン特定**で、テンプレートを編集すると URL が変わるので、デプロイ前に読み込まれたページは 404 を受け取り、意味の変わった component を描画する代わりにフルリロードへフォールバックします。

型の区別は副次的に得られます。同名でもパラメータかマークアップが違えば別の kind になります。ただし**パッケージは含みません**。名前もパラメータもマークアップも同一なテンプレートは衝突し、命令列のテキストが同じでも外部関数はパッケージごとに解決されるため実害があります。そのため同じ kind の二重登録は上書きせず起動時に失敗します。

> [!WARNING]
> **component を登録することは HTTP エンドポイントを公開することであり、そのパラメータは信頼できない入力になります。** 誰でも `?userId=999` を送れます。これまで component の引数は、ページが認証・認可・導出を済ませた値でした。登録された component は、呼び出し側が送ってきたものをそのまま受け取ります。渡された値を整形するだけの component は安全に登録できます。識別子からレコードを読み込む component は、通常のハンドラと同じように所有権や可視性を自分で確認しなければなりません。**登録がレビューの地点です。**

再描画は GET なので、繰り返し実行しても観測可能な影響が無い必要があります。後発リクエストによる再試行があり、キャッシュから返る可能性もあるためです。ユーザー固有の出力は private を明示してください。URL だけで応答が決まるからです。

> [!TIP]
> 状態を URL に入れられるなら URL に入れて、ページ遷移差分を使ってください。再描画が価値を持つのは、共有 URL に出したくないウィジェット内部の状態か、入力を本当にブラウザ側が所有している領域です。

### 3つ目のモードが無い理由

2つのモードはきれいに分かれます。ブラウザが所有する入力なら再描画、サーバが導出しなければならない入力ならページ遷移です。中間の選択肢 — ハンドラを再実行し、パラメータを1つだけ差し込み、1領域だけ返す — は魅力的に見えますが、成立しません。

パッチは対象コンポーネントにしか届かないので、そのコンポーネントの**他の入力を生んだデータ取得には影響できません**。テーブルにソート順を差し込んでも、ページの `ORDER BY` はそれを見ないので同じ行が返ってきます。つまりこのモードが扱えるのはデータ取得より下流の表示だけで、実際よりずっと汎用に読めてしまう契約になります。

しかも両側から回避できます。クエリに効かせたい状態は URL に置けばよく、そこはページ遷移が既に担当していて、共有・ブックマーク・戻るボタンまで手に入ります。URL に出したくない状態なら、そのコンポーネントが自分でデータを取得すべきで、それはまさに reloadable として登録できる条件そのものです。

## 操作と再描画を1往復で

操作してから取り直すのは、1つの操作に対して2往復で、しかも2回目はハンドラが既に知っていたことを導出し直しています。更新系のエンドポイントは、その操作が変えた領域をそのまま返せます。

```go
func addToCart(w http.ResponseWriter, r *http.Request) {
    count, err := cart.Add(r.Context(), itemID)
    if err != nil {
        httpbind.WriteError(w, r, err)
        return
    }
    if options.WantsUpdate(r) {
        _ = options.WriteUpdate(w,
            htmlupdate.Replace("cart", CartBadge(CartBadgeParams{ID: "cart", Count: count})),
            htmlupdate.Replace("row-"+itemID, ItemRow(ItemRowParams{ID: "row-" + itemID, Item: item})),
        )
        return
    }
    httpbind.Write(w, r, result) // そのエンドポイント本来の JSON
}
```

```js
const response = await fetch("/cart/add", {
  method: "POST",
  headers: { ...tinybind.updateHeaders(), "X-CSRF-Token": token },
  body,
});
await tinybind.apply(response);
```

render ヘッダが無ければ、エンドポイントは従来どおりの応答を返します（API なら JSON、フォームハンドラならリダイレクト）。ブラウザ以外のクライアントも、ランタイムを持たないページも影響を受けません。分岐点は `WantsUpdate` の1箇所だけで、これが2つの経路の乖離を防ぎます。

本文は再描画が返すのと同じ形式なので、クライアントは1つの適用コードで両方を扱えます。操作によってユーザーの居場所そのものが変わった場合は、領域の列挙の代わりに `WriteNavigate` を使います。

**クライアントはステータスに関わらず領域を適用します。** 却下された送信は 4xx を返し、そこに載っている領域が**まさにバリデーションエラーそのもの**だからです。表示することが目的です。ここは再描画と逆で、あちらは非 2xx がレンダリング失敗を意味するのでフォールバックします。

再描画と違い、信頼境界は増えません。ハンドラが操作を認可し、どのコンポーネントを描くかを Go の中で選ぶので、呼び出し側から引数が来ないためです。ただし状態を変えるので CSRF 保護が要り、応答はキャッシュ不可です。

## ストリーミング

差分は1つのバッファされたボディではなく**レコードの流れ**としても届けられます。応答の終わりを待たず、書かれた端から各領域が適用されます。`options.Render` の代わりに `options.RenderStream` を使うだけで、交渉の仕組みは変わらないので、ストリームを扱えないクライアントには従来どおりドキュメントが返ります。

```text
{"r":"head","v":1,"head":["<link …>"]}
{"r":"op","kind":"replace","id":"c2","html":"<p …>","frame":"Nk9…"}
{"r":"op","id":"c1","frame":"8Qv…"}
{"r":"end"}
```

`options.RenderStreamAsync` は同じストリームに await 境界を載せます。領域はフォールバックを伴って先に届き、置換はその後から来るので、遅い依存が足を引っ張るのは自分の領域だけです。`options.RenderLiveStream` はその上で live の購読を張り続けます。

2種類のレコードが同じストリームを共有するのは、どちらも「領域が用意できた」を意味するからです。`op` は境界を instance で名指し、`await` は既に設置済みの境界の内側にあるプレースホルダを名指します。

各レコードは自分のマニフェスト断片を運びます。末尾に全体マニフェストを置く方式は、それが記述する操作より先に書けないため成立しないからです。変化しなかった境界も、マークアップ無しで validator だけを載せて現れます。クライアントが受け取ったものだけからマニフェスト全体を組み直せるようにするためです。

ストリームは明示的な終端で終わり、それが「完走した」と「途中で切れた」を区別する唯一の手段です。終端なく止まったストリームは状態を不明にします。適用済みの操作は巻き戻さず、マニフェストを破棄し、次のリクエストは完全なドキュメントになります。

最初のレコードを書いた時点でステータスは確定するため、差分と完全ドキュメントの選択はそれより前に済ませます。

## 一貫性

1つの差分応答は、それが対象とする境界群についての単一の整合したレンダリングです。ドキュメント全体はそうではありません。再描画を独立に行った後は、領域ごとに異なる時点のレンダリングが混在し得ます。

これはバグではなく、**明文化された境界**です。複数の領域で一致していなければならない値は、1つの境界の中か、両者の祖先に置いてください。

応答にはフェンスが掛かります。後発のページ遷移に追い越された応答は適用せずに破棄し、base revision が古い境界応答は拒否し、追い越されたリビジョン向けの非同期完了は捨てます。順序が入れ替わった応答が古い状態を復活させることはありません。

サーバが描画した後に応答が破棄され得る以上、**再描画は繰り返し可能で副作用が無い**必要があります。更新処理は通常のハンドラの仕事です。

## ブラウザ側の状態の保護

領域を置き換えると、その中でブラウザが所有していたものが失われます。フォーカスとテキスト選択、変換中の IME、file input の選択、メディアの再生位置、custom element の内部状態などです。

ランタイムは可能な限りこれを避けます。変化していない境界には触れず、穴あき置換は生きたノードを作り直さずに移動させ、フォーカスを復元し、IME 変換中は更新の適用を遅らせます。避けられない場合は領域を preserve として指定してください。ランタイムはサーバ版を採用せず、既存ノードを移動します。

フォームの値についてはサーバのレンダリングが正です。したがって、非制御の input を含む境界を置換するとユーザーの入力が失われます。そうした input は境界の外に出すか、preserve を付けるか、リセットされることを承知の上で受け入れてください。

### 領域のどこまでに触れるか

丸ごと差し替えは鈍器で、ページ全体が変わる完全なページ遷移には適切です。フォームを含む領域への検索パラメータ更新や live 配信には不適切です。

最終形は**静的・動的分割**です。ここではテンプレートが既に命令列へコンパイルされているので、コンポーネントのどこが固定マークアップでどこが動的な穴かを生成時に把握しています。クライアントは静的な骨格を保持し（コンポーネント種別ハッシュが内容アドレスなので、骨格は不変で恒久的にキャッシュでき、デプロイで無効化されます）、更新は変わった穴の値だけを送ります。適用は推測ではなく確定になり、各穴の位置は既知でその周囲には一切触れないので、フォーム値・フォーカス・メディア・イベントリスナは規則としてではなく構造として保たれます。

live の制約が緩むのもこれによってです。今 live 領域がフォーム部品を禁じているのは、配信のたびに subtree が置き換わるからです。値が変わっていない穴が何も出力しなくなれば、規則は「部品の値そのものを live な穴にするな」になります。要素ごと禁止するよりはるかに自然な制約です。

どちらの方式も、**画面にある既存の行**と**サーバが返した新しい行**の対応付けを必要とします。そのための **list key** です。

```text
{for item in items}<li key={item.ID}>{item.Label}</li>{/for}
```

key が無くても、位置で対応付ければ最終的なマークアップは正しくなります。狂うのはマークアップが記述していないほうで、先頭に1行挿入するとフォーカス・開いたメニュー・チェック状態・再生中の動画がそれぞれ隣の行へ移り、トランジションも再生し直します。key はデータ側から取る必要があります（内容ハッシュは内容が変わった瞬間に同一性を失い、それは同一性が最も必要な場面です）。またキー付きループ本体は単一ルート要素である必要があり、これは更新境界と同じ制約・同じ理由です。

そこへ至るまでの中間として、**モーフィング**（新旧のツリーを突き合わせてその場で書き換える。Turbo や LiveView と同じ手）は、作者が何も印を付けずに利点の大半を得られます。代償はヒューリスティックで、キーの無いリストで対応付けを誤ります。保存島はどの段階でも有用なままです。サーバが所有していないサードパーティ製ウィジェットは、どの方式でもパッチできないためです。

### フォーム部品は別の問題

保存島は「この subtree に触るな」という指示です。上流の選択に応じて option が変わる `<select>` には、これは不適切な道具です。option の一覧は**変わらなければならない**のに、現在の選択はしばしば残ってほしいからです。

理由は、クライアント側の状態に2種類あることです。フォーカス、テキスト選択、IME 変換、スクロール位置、メディアの再生位置は**ノード**に属していて、その要素が生き残らない限り失われます。選ばれた option、チェック状態、入力されたテキストは**値**に紐付いていて、それを載せていたノードとは独立に意味を持つので、置換を越えて生き残れます。

2つ目の種類の引き継ぎには、作者の印も追加の記録も要りません。HTML が既に「サーバが言ったこと」と「ユーザーがしたこと」を分けているからです — `value` と `defaultValue`、`checked` と `defaultChecked`、`selected` と `defaultSelected`。

手順は4つの突き合わせでできています。

1. **変更検出** — 同じ要素の `value` と `defaultValue` を比べ、食い違っていればユーザーが触った部品として記録します。両側とも DOM が既に持っているので、スナップショットは要りません。
2. **部品の同定** — 更新後の DOM で相手を見つけます。要素は作り直されているかもしれないので、`name` を鍵に（無ければ位置で）対応付けます。
3. **適用可能性** — 記録したユーザーの値が、新しい option や radio の集合にまだ存在するかを確かめます。`select` と radio にだけ必要で、テキストやチェックボックスには不要です。
4. **主張の変化** — 更新前の default と更新後の default を比べます。

最後の比較が衝突の決着になります。**サーバの default が変わっていれば**サーバが新しい値を主張しているので勝ち。変わっていなければサーバは何も言っていないので、ユーザーの値が残ります。沈黙を主張と解釈すると、無関係な更新のたびに入力済みのテキストが消えます。

これは更新が触れるすべての領域で**既定で有効**です。無効にする手段も、1回の応答だけユーザー状態を破棄する手段もありません。入力したテキストが消えるのはユーザーが必ず気付く失敗であり、オプトインにすると「全作者が忘れずに書く」か「全作者のフォームが壊れる」かのどちらかになります。

記録した値が通用しなくなった場合は、ブラウザの alert で通知します。これは意図的に暫定です。今は黙って失うほうが悪い結果ですが、選択肢から値が消えるのは多くの場合バグではなく通常のアプリ挙動なので、いずれアプリ側が購読して自分で判断できるイベントに置き換わります。

常時有効にすることで、穴が1つ残ります。サーバは「**変わっていない default に戻したい**」を表現できません。フォームを空にしたい場合、サーバは前回と同じ空の default を描画するので、決着規則はそれを沈黙と読み、ユーザーのテキストが残ります。default をどう比べても2つの状況は区別できません。マークアップが同一だからです。ただし実害はほとんどありません。フォーム送信は GET ではないのでランタイムは傍受せず、応答は完全なドキュメントになり、照合すべき領域が存在しないからです。post-redirect-get はこの規則の外で、通常のページ読み込みとしてフォームをクリアします。表現できないまま残るのは「GET の更新でフォームを空にする」場合だけです。

file input はこれら全ての例外で、選択を値から復元する手段がそもそも無いので、保存島に入れるか領域の外へ出してください。

### 保存島

サーバがそもそもパッチできない領域があります。サードパーティ製ウィジェット、canvas、サーバが所有していないメディア要素など。印を付けるとランタイムはサーバ版を採用せず、生きているノードを置換後のマークアップへ移すので、ノードとブラウザがそこに付けたものが丸ごと残ります。

```html
<div data-tb-preserve="player">…</div>
```

この目印も設定した接頭辞に従うので、`pw` を使うプロジェクトでは `data-pw-preserve` になります。

キーが描画をまたいで領域を対応付けます。置換側に対応するキーが無ければ、それは新しい領域なので、無関係なノードを差し込まずサーバ版をそのまま使います。

## 設定

コード生成:

```go
//go:generate go run github.com/shibukawa/tinybind-go/cmd/tinybind-gen generate -dir . -data-attribute-prefix tb
```

`-data-attribute-prefix` は生成される属性の名前空間で、既定では `data-tb-id` になります。同じ接頭辞がプレースホルダ要素と境界 ID も名付けるので、`pw` を設定したプロジェクトでは境界が `data-pw-id`、プレースホルダが `<pw-boundary id="pw-1">` になります。命名体系は2つではなく1つです。属性を書くのは生成器、読むのはランタイムなので、`Options.DataAttributePrefix` にも同じ値を設定してください。

配信。プロトコルがドキュメントに書き込む名前はすべて設定可能で、フレームワークが所有するものは2つの名前空間の内側にあります。

```go
options := htmlupdate.Options{
    Key:                 validatorKey, // 公開ページ以外では必須
    PathPrefix:          "/_tb",       // フレームワークの全エンドポイント
    HeaderPrefix:        "X-Tinybind", // フレームワークの全ヘッダ
    DataAttributePrefix: "tb",         // 属性・要素・識別子のすべて
    GlobalName:          "tinybind",   // ランタイムが自分を置く名前
    MaxManifestBytes:    8 << 10,      // 超過したヒントは拒否ではなく破棄
    MaxQueryBytes:       4 << 10,      // 超過した再描画クエリは拒否
}

if err := options.Validate(); err != nil {
    return err // 要素名にできない接頭辞などを起動時に検出
}

options.Mount(mux, registry) // ランタイムアセットと再描画エンドポイント

mux.HandleFunc("GET /search", func(w http.ResponseWriter, r *http.Request) {
    wrappers := []htmlbind.Wrapper{BindDocument(...), BindLayout(...)}
    leaf := Page(PageParams{Query: r.URL.Query().Get("q")})
    if err := options.Render(w, r, wrappers, leaf); err != nil {
        http.Error(w, "render failed", http.StatusInternalServerError)
    }
})
```

全エンドポイントが1つの接頭辞の下にあるということは、ルーティング規則もキャッシュ規則もアクセス制御も1つで全体を覆えるということです。`Mount` がまとめて登録し、フレームワークが所有するものがその外に出ることはありません。

`options.Render` はモードを判定し、`Vary` を設定し、ドキュメントか差分のどちらかを書きます。それ以外のレスポンスに関する判断は、このモジュールの他の部分と同じく利用者の責務のままです。

ランタイムは同じ接頭辞の下、内容ハッシュ付きのパスで配信されるので、恒久的にキャッシュ可能でありながらデプロイで無効化されます。読み込む要素は `options.ScriptTag()` が返し、その要素が設定一式を運ぶので、共有された1つのランタイムアセットがどんな名前の組み合わせでも再ビルドなしに動きます。バイト列に焼き込まれているのはプロトコルバージョンだけです。

### ランタイムを自分で持つ

すでにブラウザランタイムを配っているフレームワークは、2本目を足してはいけません。1つのドキュメントにランタイムが2つあるということは、境界 ID の空間が2つ、ビルド識別子が2つ、そしてどちらがどの領域を持つのかを決めるものが無いまま script タグが2つある、ということだからです。バイト列を受け取って統合してください。

```go
options := htmlupdate.Options{Key: validatorKey, CallerOwnsRuntime: true}

source := htmlupdate.RuntimeSource()      // 名前に依存しないバイト列
asset := options.RuntimeAsset()           // バイト列・ダイジェスト・MIME型・ファイル名
config := options.RuntimeConfig()         // 統合したランタイムに渡すべき設定
```

`CallerOwnsRuntime` を立てると `Mount` はアセットの経路を登録せず、`ScriptTag` は空文字を返します。このビルドが配信していないアセットを指す script タグは、タグが無いことより悪いからです。統合したアセット側では同じ名前を持つ config で `createPartialUpdateRuntime(config)` を呼び、結果を好きな名前に置いてください。

避けるべきなのは `runtime.js` の複製を持つ形です。複製はバージョン固定された依存ではないので、アップグレードで上流が変わってもビルドは何も失敗せずに乖離していき、乖離したブラウザランタイムはコンパイルエラーではなく「静かに死んだページ」として現れます。

### 失敗を報告する

再描画エンドポイントは URL を所有しているので、レスポンスを書く責任があります。ただし「失敗がどう見えるか」を決める責任はありません。

```go
options.OnFailure = func(w http.ResponseWriter, r *http.Request, f htmlupdate.Failure) {
    logger.ErrorContext(r.Context(), "redraw failed", "kind", f.Kind, "err", f.Err)
    problem.Write(w, r, f.Status, f.Kind.String()) // または htmlupdate.WriteFailure(w, f)
}
```

拒否された再描画はすべてここに来ます。壊れたパス、公開していない kind、別ビルドのページ、大きすぎるクエリ、復号できない引数、失敗した描画のいずれについても、パッケージが書いたはずのステータスと本文、そして原因がある場合はその原因が渡ります。フックを設定しなければ、これまでどおりパッケージ自身が既定の応答を書きます。

再描画のレスポンスは描画結果に対する `ETag` と `private, no-cache` を持つので、変化していない領域はマークアップ全体ではなく `304` で済みます。公開してよい再描画や、別の条件を要求するプロキシがある配信では `RedrawCacheControl` でこの方針ごと差し替えられます。

HTTP 層が `htmlbind` ではなく `htmlupdate` にあるのは、生成されたテンプレートコードが TinyGo や WebAssembly で動き続けられるよう、描画ランタイムを `net/http` から切り離しておくためです。

## 制限と非目標

- 差分の粒度は境界単位です。属性単位やテキストノード単位の差分は取らず、変化した境界は丸ごと置き換えます。
- 境界は、入力とサーバ状態が同じなら決定的に描画される必要があります。タイムスタンプを埋め込んだ領域は毎回不一致になり、毎回送信されます。
- マニフェストのサイズは境界の数に比例します。境界はリストの各行ではなく、意味のある領域に置いてください。
- 更新の状態はサーバではなくブラウザが持ちます。セッションアフィニティは不要、再起動で失うものは無く、古いヒントは完全ドキュメントに退化するだけです。
- これはクライアントサイドフレームワークではありません。ブラウザ側の component 状態も、仮想 DOM も、クライアント側のルーティングテーブルもありません。マークアップの正はサーバのままです。
