# cachekeybind guide

`cachekeybind` generates the cache key method for a Go struct. Mark the fields a
cached result depends on, run the generator, and no call site concatenates
anything by hand.

A hand-written key fails quietly. Omit the type's identity and two key types
holding equal field values reach one entry — the first caller's result answers
the second, which is a wrong answer rather than a stale one. Concatenate without
framing and `"ab"+"c"` reaches the same entry as `"a"+"bc"`. Neither shows up as
an error; both show up as one user seeing another user's data. That silence is
what this package is built against.

What it does not do is guess your dependency set. Marking is opt-in, and a
dependency you never mark is absent from the key. See
[What generation guarantees](#what-generation-guarantees) for why the line sits
there.

## What you write, what you get

You write a tagged struct and a `go:generate` line:

```go
package app

//go:generate go run github.com/shibukawa/tinybind-go/cmd/tinybind-gen -dir .

type UserSummary struct {
	UserID string `cache:"key"`
	Page   int    `cache:"key"`
	Name   string
	Total  int
}
```

You get one method and one assertion:

```go
// Code generated by tinybind; DO NOT EDIT.

var _ cachekeybind.CacheKey = UserSummary{}

func (v UserSummary) CacheKey() string {
	return cachekeybind.KeyString("example.com/app.UserSummary") +
		cachekeybind.KeyString(v.UserID) +
		cachekeybind.KeyInt(v.Page)
}
```

`Name` and `Total` are the result, not the query, so they are absent from the
key. That is the whole point of marking: see the next section.

The runtime interface is one method:

```go
type CacheKey interface {
	CacheKey() string
}
```

The returned string carries field values in plaintext. It is safe to concatenate
with a scope prefix and it must never reach a browser.

## The `cache` tag

One spelling, and nothing else:

| Spelling | Where | Meaning |
|---|---|---|
| `cache:"key"` | an exported field | the field is part of the key |

An unmarked field is not in the key. There is no exclusion spelling, because
there is nothing to exclude from — and no other option, because the identity is
wholly derived.

## Why marking is opt-in

Because the struct you pass to a cache is often a storage entity rather than a
purpose-built key:

```go
type Reading struct {
	Sensor  string  `dynamo:"sensor,partitionkey" cache:"key"`
	At      int64   `dynamo:"at,sortkey"          cache:"key"`
	Celsius float64 `dynamo:"celsius"`
}
```

An entity's fields are mostly what the fetch returned. If every field were keyed
by default, `Celsius` would be in the key, and you could only build the key from
the value the lookup exists to avoid fetching. Over an entity, default-include is
not slow — it is unusable.

Nothing checks your `cache` marks against your `dynamo` or `firestore` tags. The
two answer different questions: a storage key says where the row is, a cache key
says what the result depended on. They legitimately differ in both directions — a
list cached by partition key alone is narrower, and a key carrying a page number
that is never stored is wider. A check would fire on correct code.

## One struct, one key

A struct yields one key. The key is composite when several fields are marked.

If you need the same entity under two different queries, define two structs. The
identity below is derived from the package path and type name, and that is only
unique by construction while the relation stays one-to-one — a type carrying two
keys would need you to name them, which is the restating this package exists to
remove.

## Identity

The identity is `<package path>.<TypeName>`. Both parts are derived. Nothing in
it is declared, so nothing in it can be forgotten.

**There is no key version.** It was considered and dropped. A version is a number
you must remember to raise when the *meaning* of a result changes but its fields
do not — and forgetting it is silent, so it would relocate a failure rather than
close one. That is the failure class this package exists to reduce, not add to.

Invalidating on a meaning change is a deployment's job, and the module already
says so: `CacheStore` never enumerates or invalidates entries, and expiry is the
only removal path the runtime relies on. So when meaning changes without the
fields changing, use what your deployment already has:

- **Namespace the store per build or per release.** A framework that keys on
  build identity already invalidates on every deploy, which covers the common
  case — you changed the code.
- **Flush the affected prefix.** The scope prefix makes that a range delete.
- **Wait out the TTL**, if it is short enough to be an answer.

Renaming the Go type also changes every key, and the compiler finds each call
site. It is a real option for a purpose-built key struct — but not for a storage
entity, where the type name feeds the Datastore kind or the table mapping and
renaming it would repoint your storage as a side effect.

## Field types

| Go type | Helper |
|---|---|
| `~string` | `KeyString` |
| `~bool` | `KeyBool` |
| every signed integer width, including named types | `KeyInt` |
| every unsigned integer width | `KeyUint` |
| `~float32`, `~float64` | `KeyFloat` |
| `[]byte` | `KeyBytes` |
| `time.Time` | `KeyTime` |
| pointer to any of these | `KeyOptional` |
| slice of any of these | `KeyArray` |

Pointers and slices nest, so `*time.Time` and `[][]int` both work.

A field type with no framing — a struct, a map, a channel — is a generation
error, not a skipped field. A skipped field is exactly the silent wrong answer
this package removes; key on the fields it is derived from instead.

## What generation guarantees

It guarantees:

- the identity prefix is present, so two key types never collide;
- every value is length-prefixed, so a concatenation can only be split one way;
- a hand-written `CacheKey` is never silently replaced.

It does not guarantee your dependency set is complete. Add a parameter to the
fetch, forget to mark it, and the key does not change. No compiler can see that
requirement. What generation removes is every failure that survives a *correct*
dependency set — which is both of the wrong-answer failures, leaving the one you
are looking straight at while you add the dependency.

The one case it does catch: a struct reached as a key with **no** marked field is
a generation error. An identity-only key would give every instance of the type a
single shared entry.

## Generation

Two ways a type is discovered.

**By tag.** Under generate-all, any struct carrying a `cache` tag gets a key. A
struct with no `cache` tag is not a key type and is left alone.

**By call site.** A framework registers the call that reads a key, and the key is
an argument type:

```go
calls := generator.NewCallRegistry()
err := calls.Register(generator.CacheKeyCall(
	generator.Function("example.com/framework", "Memo"),
	generator.ArgumentType("key", 1),
))
```

`ArgumentType` rather than `GenericType`: a memo call is generic over the result
it caches, and the key is the value beside it.

Turn generation off with the `cache-key` feature flag.

## Generation errors

| Message | Cause |
|---|---|
| `marks no field` | a struct reached as a key with nothing marked |
| `has no cache key framing` | a struct, map or other unframeable field type |
| `already declares CacheKey` | a hand-written method the generated one would collide with |
| `unknown cache tag option` | anything but `key` |
| `a blank field carries no value` | a `cache` tag on a blank `_` field |
| `cannot be marked` | an unexported or embedded field carrying `cache:"key"` |

## Framing helpers

The helpers are exported, so a hand-written key is possible where generation does
not reach. Every value is written as its byte length, a colon, and the value.

```go
cachekeybind.KeyString("abc")  // "3:abc"
cachekeybind.KeyInt(42)        // "2:42"
```

Two details worth knowing:

- `KeyOptional` distinguishes absence from every present value, so a nil pointer
  and a pointer to the zero value are different keys.
- `KeyArray` writes the element count first, so one two-character element cannot
  collide with two one-character ones. A nil slice and an empty slice frame
  alike, because they are equal as inputs to a fetch.

These are `cachekeybind`'s own, not `htmlbind`'s. The component output cache
frames its keys with the same rule but its own set; the two caches have separate
identity spaces, so no key is ever compared across them.
