id: decision:implicit-binding-declaration-site
type: decision
title: Where An Implicit Binding Is Declared
---
Two candidates for requirement:embedder-implicit-bindings, differing in whether two compilations can disagree; declaring per compilation and folding the reached set up the chain is the recommendation, because it makes a disagreement detectable rather than merely unlikely.

```yaml
source:
  - requirement:embedder-implicit-bindings, the request's open contract 3
  - read against data:generator-options and htmlbind foldSlots, 2026-08-16
review_gate: approved 2026-08-16 by the owner
decided: 2026-08-16 by the owner; per compilation plus the folded reached set, the shadowing error, and one optional axis per binding — every recommendation below as written
what_exists_today:
  channel: options are Go values the embedder constructs, and api:generator-call-registration returns an immutable snapshot per generate invocation
  no_project_file: there is no project-level configuration file in this module, so per project is a mechanism that would have to be invented rather than a place that already exists
  the_hazard_is_documented: requirement:route-package-context-externals is exactly this failure — one field filled on the templates path and not on the route path, shipping a feature that was simply absent on filesystem routes
candidates:
  per_compilation:
    shape: the binding set is part of data:generator-options, like every other embedder-supplied name
    benefit:
      - no new mechanism; it is the seam requirement:builtin-element-registration and every discovery option already use
      - a framework that builds one snapshot and passes it everywhere gets project-wide behavior for free
      - a test compiling one template can declare its own set without a project fixture
    cost:
      - nothing enforces that two compilations agree, and this module compiles templates on more than one path
      - divergence is silent: a template compiled without a binding it uses fails to resolve, and one compiled with a binding the render never supplies renders empty
      - a component from another package under decision:library-component-seams was compiled against its own set, which the application never sees
  per_project:
    shape: one authoritative declaration for everything generated, checked for consistency
    benefit:
      - a binding is language-level scope, and a component's meaning should not depend on which invocation compiled it
      - divergence becomes a hard error rather than a rendering difference
    cost:
      - the project is not a thing this module models; it would gain a configuration surface it has avoided
      - it does not actually solve the library case, because a library is generated by its own project
      - decision:framework-integration-seams keeps embedder-supplied identity in options values, and this would be the first exception
decision:
  chosen: per_compilation, plus recording the reached set in the plan; approved 2026-08-16 by the owner
  one_walk_two_consumers: the reached set the plan records is the same set decision:implicit-binding-cache-identity keys on, so the call-graph walk runs once and feeds both the cache key and the composition check
  what_a_caller_can_now_do: read a fragment's required bindings before rendering it, and refuse or report a composition it cannot supply values for
  the_addition: a plan records which bindings its ops read, folded up the chain in foldSlots beside head, assets, vary, and the decision:cache-scope-declaration private bits, and readable on Fragment and Wrapper
  what_it_buys:
    - a composition assembled at run time from separately generated parts reports what it needs, so a library component reaching a binding the application never declared is detectable at the seam rather than at the pixel
    - the render can refuse, or report, a fragment whose required set is not covered by the values supplied
    - it is the same shape decision:cache-scope-declaration already used for a security-relevant fact that had to survive a run-time combination generation never saw
  what_it_costs: one more folded field, and the diagnostic wording for a fragment whose requirement the caller cannot satisfy, which requirement:head-contribution-provenance already has a precedent for
  why_not_simply_per_project: it would make two compilations agree by construction and still leave the library case open, so the fold is needed either way; once the fold exists, per project buys little
shadowing:
  decided: 2026-08-16; the error, as the request asked and as recommended below
  request: a parameter taking a declared name is an error naming the collision
  alternative_considered: let the parameter win, on the reading that a local name is more specific
  why_the_error_is_right: a silently shadowed framework value renders whatever the parameter holds, in every position the binding was supposed to serve, and the author who wrote the parameter is not the author who declared the binding
  report: at the parameter position, naming the binding and where it was declared, as decision:cache-scope-declaration reports a component that declared a scope a caller cannot satisfy
vary_axis_shape:
  cause: decision:implicit-binding-cache-identity leaves the axis to the embedder, so the declaration has to carry it
  candidates:
    per_binding_optional_axis: one axis name beside the kind, empty for a binding the URL already distinguishes; smallest, and matches data:builtin-element-definition Vary
    separate_registration: axes declared apart from bindings; more flexible and lets one axis cover several bindings, at the cost of a second list to keep in step
  decided: 2026-08-16; per_binding_optional_axis, because the two facts are read together everywhere they are read at all
```
