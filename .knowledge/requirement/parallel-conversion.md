---
id: requirement:parallel-conversion
type: requirement
title: Parallel Conversion
---
Discover every value the registered hooks will claim before compiling anything, convert those values concurrently, and let the sequential compile find each answer already waiting.

```yaml
priority: could
review_gate: implemented 2026-08-04, needs user approval as built
as_built:
  surface: htmlbind.CollectReferences for discovery, generator Options.ConversionWorkers for the switch
  where: templates/htmlbind/hook.go for the collect mode over the rewrite walk; generator/hooks.go for the memo, the prewarm, and the atomic store
  collect_mode: the rewrite walk itself, with every side effect suppressed, so a value discovery misses is one the rewrite would miss too rather than a second walk that could drift from it
  reports_nothing: an overlap, a dynamic reference, and a strict failure are all left to the compiling pass, so which diagnostics a build has never depends on whether discovery ran
  single_flight: a per-key sync.Once, with the lock released before the conversion, so an encode never serializes the memo
  errors_deferred: a failure is memoized like a success and raised by the compile that needed the value, which keeps the reported error the first in template order
  atomic_store: a cache entry is written to a temporary file and renamed, because a concurrent or interrupted run must leave a whole entry or none
  guarded: conversionCache.sources takes a mutex, since every worker writes to it while building its key
  worker_floor: fewer than two claims starts nothing, so a small module pays no setup
hash_exclusion_decided:
  question: whether the worker count belongs in the hashed options at all, which this requirement raised and building answered
  answer: excluded, with a json:"-" tag
  why: it was in the hash by default and made a build with workers set produce different bytes from one without, which is the exact property this requirement promises not to break
  wider_reason: every other option can change what is generated and this one cannot; hashing it stamps the machine into the output, so a four-core laptop and a sixteen-core runner would disagree on identical work and `--check` would fail between two correct builds
discovery_reporting_decided:
  question: whether discovery should also report dynamic references so a strict run could fail before converting
  answer: no
  why: it would make a strict build's diagnostics depend on whether the switch was set, which is the one thing this requirement will not trade for speed; a strict run that converts and then fails is slower and says the same thing
tested:
  - TestParallelConversionProducesIdenticalOutput, over one directory and one derived root so the worker count is the only difference
  - TestParallelConversionOverlaps, which asserts overlap directly rather than timing the build: each transform waits for the others to start, so a serialized implementation fails with a message instead of a slow pass
  - TestParallelConversionConvertsEachValueOnce, the single-flight memo against a repeated reference
  - TestParallelConversionDefersErrors, repeated, since a race that resolves one way most of the time is the failure this rule removes
  - TestParallelConversionWarmCacheConvertsNothing
  - TestCollectReferencesCallsNoTransform, covering head reach, dedup, dynamic values, and foreign content in one pass
  - the whole set under the race detector
source:
  - requirement:derived-asset-generation not_shipped.parallel_conversion
  - requirement:element-reference-hook conversion_timing.remaining_cost
  - downstream request from the Popcorn Wave derived asset pipeline, 2026-08-04
the_cost_being_paid:
  what: a cold cache converts one value at a time, because the compile that needs each value is sequential and the transform is called from inside it
  when: a first build and a first clone; an incremental build converts nothing and pays none of this
  why_it_was_deferred: exactly that, and the deferral was right until a project with real encoders asked
  scale: seconds per image encode against microseconds per template compile, so the conversion is the whole wall clock and the compile is noise
what_must_not_change:
  inline_outcome: the rewrite depends on how the conversion turned out, so the transform still returns bytes and still decides the value; requirement:element-reference-hook conversion_timing round_two records the resolver form being tried and rejected for exactly this, and this requirement does not reopen it
  why_this_is_different: round_two moved the conversion after the compile and lost the outcome; this moves it before the compile and keeps it, which is the opposite direction through the same problem
  sequential_compile: the compile stays one module at a time, so the report order, the diagnostic order, and the generated bytes are unchanged
  no_new_caller_configuration_to_be_correct: a caller that sets nothing gets the same output it gets today
the_shape:
  discovery:
    what: parse each template module and walk it exactly as the rewrite walk does, collecting the distinct hook and static value pairs that would be claimed
    calls_nothing: no transform runs during discovery, so discovery costs a parse and no encode
    reuses: the same walk, the same foreign-content exclusion, the same head declaration reach, so a value discovery misses is a value the rewrite would have missed too
  conversion:
    what: convert the collected pairs concurrently into the run memo
    bounded: the caller's worker count and never an unbounded fan-out, because an image encoder is CPU-bound and a goroutine per asset over a large tree is a memory problem
    no_default_fan_out: unset means one goroutine rather than a processor count, since the switch is opt-in and a default that converted concurrently would be the silent upgrade the contract change forbids; a caller wanting its processor count passes it
  compile:
    what: the existing sequential pass, whose transform calls are now memo hits
    unchanged: everything it does with the answer
  double_parse:
    cost: each module is parsed twice, once to discover and once to compile
    acceptable: parsing is microseconds against seconds of encoding, which is the same ratio that makes this worth doing at all
    alternative_rejected: holding every parsed module in memory between the two passes trades a bounded, tiny cost for an unbounded one on a large tree
contract_change_for_callers:
  what: Transform becomes callable from several goroutines at once, so it must be safe for concurrent use
  today: it is documented as a pure function of what it reads plus its own settings, which is necessary and not sufficient; a transform holding a shared scratch buffer is pure by that definition and unsafe by this one
  visibility: this is the one thing a caller must act on, so it is documented on ReferenceHook.Transform and not only here
  no_silent_upgrade: a caller that has not stated it is safe must not be run concurrently, which is what makes the switch below opt-in
switch:
  form: a GenerateOptions field naming the worker count, where unset means one and preserves today's behavior exactly
  why_opt_in: concurrency is a promise about the caller's transform that only the caller can make, and defaulting to it would silently break a transform that was correct under the shipped contract
  hashing: the field is part of the options value, so it must not change generated bytes; if it ever could, the design is wrong rather than the hash
memo_and_cache_under_concurrency:
  run_memo: the map runScopedHooks builds becomes safe for concurrent use, and gains single-flight so twenty templates naming one image still convert once when the twenty are discovered together
  named_sources: the set the conversion cache accumulates while building keys is written from every worker and must be safe too
  store_writes: two workers converting different values write different cache files, and a write is not atomic today, so a store writes to a temporary name and renames, because a reader on the next run must never see half a file
  read_before_write: a cache hit still short-circuits the transform, so a warm cache converts nothing concurrently or otherwise
memo_scope_finding:
  found: reading the generator on 2026-08-04
  fact: the run memo and the conversion cache are built inside the per-directory template pass, and one Execute covers one directory, so the in-memory memo spans a directory and not a caller's whole build
  consequence: a caller invoking Execute once per package directory dedupes across directories only through the on-disk cache, which needs a hook that declares a CacheKey and a configured directory; without either, one image referenced from two directories converts twice
  relation_to_this_requirement: discovery has the same boundary, so parallelism is per Execute and a caller wanting more overlaps its own Execute calls
  worth_stating_separately: requirement:derived-asset-generation reuse_across_units reads as a stronger promise than the in-memory memo makes, and the difference is the cache
error_reporting:
  problem: several conversions may fail at once, and reporting whichever goroutine lost the race would make the message nondeterministic
  rule: a conversion failure is stored in the memo and surfaces at the compile that needed it, never at conversion time
  effect: the reported error is still the first failure in template order, with the same file, line, and column it has today
  no_early_exit: discovery having found a value that will fail does not stop the other conversions, because stopping early would make which errors exist depend on timing
determinism:
  contract: unchanged; identical inputs produce identical rewritten bytes, identical derived files, and an identical report
  order: the report is built by the sequential compile, so worker completion order is invisible
  check: a build with the switch set and a build without it produce identical output, which is the acceptance test that matters most
constraints:
  - a project registering no hook discovers nothing, starts no worker, and regenerates byte-identical Go
  - a warm cache performs no conversion whether the switch is set or not
  - the switch changes wall clock and nothing else
  - no transform is called during discovery
acceptance:
  - a cold build with the switch set produces bytes identical to a cold build without it
  - a tree of independent images converts in roughly the wall clock of its slowest encode rather than their sum
  - one image referenced from twenty elements converts once, whether discovered together or not
  - a failing conversion reports the same template position it reports today, and the same one every run
  - two conversions failing report the first in template order, deterministically
  - an unset switch calls every transform from one goroutine
  - a warm cache with the switch set starts no worker and reads every answer from the store
related:
  - requirement:element-reference-hook
  - requirement:derived-asset-generation
  - requirement:incremental-generation
  - rule:generation-input-hash
open_questions:
  - whether the discovery parse is worth keeping once a caller has many modules, since holding them costs memory and reparsing costs a second walk
  - whether a caller invoking Execute per directory should be given a way to share one memo across them, which is the memo_scope_finding boundary and the only dedup the on-disk cache does not already cover
```
